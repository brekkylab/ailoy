A turn starts with your query and ends when the model answers without asking for a tool. In between, the model can call tools any number of times. [How an agent works](/docs/concepts/#what-happens-in-a-turn) explains each step.

There are two ways to run a turn:

| Method | Returns | Use it when |
| --- | --- | --- |
| `agent.run(query)` | Each message, once it's complete | You act on whole messages |
| `agent.run_stream(query)` (`runStream` in Node.js) | Pieces of each message as the model writes them | You show the reply to a person as it's written |

The query is a string or a [message](/docs/guides/message-format/#send-an-image-or-other-content).

## Read the messages of a turn

`agent.run` returns one `MessageOutput` for each message in the turn: the model's tool calls, each tool result, and the final answer.

| Field | Description |
| --- | --- |
| `message` | The complete [message](/docs/guides/message-format/). |
| `finish_reason` | Why the model stopped: `stop`, `length`, `tool_call` or `refusal` (with a `reason`). |
| `usage` | Input and output token counts, when the provider reports them. |

The [quick start](/docs/guides/quick-start/#run-an-agent) shows a full loop that prints the text of each message.

## Stream the reply

`agent.run_stream` returns `MessageDeltaOutput`s. Each `delta` holds a small piece of a message, such as a few tokens of text. A tool result arrives as one delta. The deltas between two `finish_reason`s add up to the message that `run` would return. In Rust, the `Delta` trait's `accumulate` and `finish` combine them for you.

This prints the reply as the model writes it:

<Tabs syncKey="lang">

<TabItem label="Python" icon="seti:python">

```python
async for output in agent.run_stream("Explain what a microVM is."):
    for part in output["delta"]["contents"]:
        if part["type"] == "text":
            print(part["text"], end="", flush=True)
```

</TabItem>
<TabItem label="Node.js" icon="seti:javascript">

```js
for await (const { delta } of agent.runStream('Explain what a microVM is.')) {
  for (const part of delta.contents) {
    if (part.type === 'text') process.stdout.write(part.text)
  }
}
```

</TabItem>
<TabItem label="Rust" icon="seti:rust">

```rust
let query = Message::new(Role::User).with_contents([Part::text("Explain what a microVM is.")]);
let mut stream = agent.run_stream(query);
while let Some(output) = stream.next().await {
    for part in &output?.delta.contents {
        if let PartDelta::Text { text } = part {
            print!("{text}");
        }
    }
}
```

</TabItem>
</Tabs>

## Stop a turn early

Nothing runs until you iterate the turn. Each step of your loop moves the turn forward.

- To stop a turn, break out of the loop. In Python you can also call `aclose()` on the run. In Rust, drop the stream.
- When the next turn starts, any tool call left without a result gets a result saying it didn't run. This keeps the conversation in a form the model's API accepts.

## Continue a conversation

Every query, model message and tool result is added to the agent's history, so the next `run` continues the same conversation. Read the history with `agent.history`. In Python and Node.js, reading it while a turn is running raises an error.

To continue a conversation in a new agent, for example after your program restarts, pass the saved messages to the builder:

<Tabs syncKey="lang">

<TabItem label="Python" icon="seti:python">

```python
agent = await AgentBuilder("anthropic/claude-haiku-5-5").history(saved_messages).build()
```

</TabItem>
<TabItem label="Node.js" icon="seti:javascript">

```js
const agent = await new AgentBuilder('anthropic/claude-haiku-5-5').history(savedMessages).build()
```

</TabItem>
<TabItem label="Rust" icon="seti:rust">

```rust
let agent = AgentBuilder::new("anthropic/claude-haiku-5-5")
    .history(saved_messages)
    .build()
    .await?;
```

</TabItem>
</Tabs>

Messages are plain JSON, so you can store them anywhere and load them back as they are. If the agent worked in a sandbox, it also needs the same sandbox to continue: see [Continue the work later](/docs/guides/sandbox/#continue-the-work-later).

## Handle errors

A turn ends with an error, instead of a message, in these cases. The agent stays usable afterwards.

| What happened | What Ailoy does |
| --- | --- |
| The model fails before its first message, for example because its API is down or a key is wrong | Removes your query from the history, so you can run the same query again. |
| The model hits its output limit | Returns the cut-off reply and keeps it in the history, then raises an error. Your next query can ask for the rest. |
| The model's API rejects an image in a tool result | Replaces the image with a note and sends the request again, once per batch of tool results. A second rejection ends the turn. |

A failing tool doesn't end the turn. An unknown tool, a missing sandbox, an exception in your function or a failed command becomes that call's result, and the model can try something else.

The error types:

- **Python:** Ailoy's own errors are `AiloyError`. Sandbox failures are virtx's `VirtxError`, with the server's `status`.
- **Node.js:** errors from the agent have `code` set to `AILOY_ERROR`, or `VIRTX_ERROR` for a sandbox failure. Calls on the virtx package itself, such as `createSandbox`, throw virtx's `VirtxError`, with `source` and `status`.

See [Errors](/docs/sdk/errors/) in the SDK reference.

## Track token usage

Each model message's `MessageOutput` carries `usage` with input and output token counts, when the provider reports them. `input_tokens` counts all input, cached or not. A long run's input grows with every tool result; [Manage context](/docs/guides/context-manager/) keeps it under a limit.
