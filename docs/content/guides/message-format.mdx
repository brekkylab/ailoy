Everything an agent sends and receives is a message. Ailoy uses the same message format for every model provider and converts it to the provider's format when it calls the model. You read messages from `agent.run`, and you can send one to pass more than text, such as an image.

A message has a role and a list of parts:

```json
{
  "role": "user",
  "contents": [
    { "type": "text", "text": "Can you explain how photosynthesis works?" }
  ]
}
```

In Python a message is a `dict`, and in Node.js a plain object, with exactly this shape. In Rust it is `ailoy::message::Message`. The [Types](/docs/sdk/types/#message) reference lists every field.

## Roles

| Role | Written by |
| --- | --- |
| `system` | The agent, from your instruction. Always the first message. |
| `user` | You, or your app's end user. |
| `assistant` | The model. |
| `tool` | A tool, with the result of a call the model asked for. |

You don't write the system message yourself. The agent builds it from `.instruction(...)`, the list of its [skills](/docs/guides/skills/) and its [memory](/docs/guides/memory/), and puts it first in the history. If you pass a history that already starts with a system message, the agent keeps that one as it is.

## Message fields

| Field | Description |
| --- | --- |
| `role` | One of the roles above. |
| `contents` | The content, as a list of parts. |
| `thinking` | The model's reasoning, kept separate from `contents`. Only on assistant messages from reasoning models. |
| `tool_calls` | The tools the model wants to call, as `function` parts. Only on assistant messages. |
| `id` | On a `tool` message, the id of the call it answers. |
| `signature` | A signature the provider issues for `thinking`. Ailoy sends it back unchanged on the next request. |

Because reasoning and tool calls have their own fields, `contents` only ever holds what the model says.

## Parts

A part is one piece of content. A message with text, an image and more text has three parts.

| `type` | Shape | Used for |
| --- | --- | --- |
| `text` | `{ "text": "..." }` | Plain text. |
| `image` | `{ "image": { "type": "url", "url": "..." } }` or `{ "image": { "type": "embedded", "mime_type": "image/png", "data": ... } }` | An image, by URL or as bytes. |
| `function` | `{ "id": "...", "function": { "name": "...", "arguments": { ... } } }` | A tool call, inside `tool_calls`. |
| `value` | `{ "value": ... }` | Any JSON value, such as a tool result. |

:::tip
Some providers, such as Gemini, don't accept image URLs. Embedded bytes work with every provider that accepts images.
:::

## Send an image or other content

`agent.run` accepts a string or a message. A string becomes a user message with one text part. To send anything else, such as an image, pass a full message:

<Tabs syncKey="lang">

<TabItem label="Python" icon="seti:python">

```python
from pathlib import Path

query = {
    "role": "user",
    "contents": [
        {"type": "image", "image": {"type": "embedded", "mime_type": "image/jpeg", "data": Path("dog.jpg").read_bytes()}},
        {"type": "text", "text": "What do you see in this image?"},
    ],
}
async for output in agent.run(query):
    ...
```

</TabItem>
<TabItem label="Node.js" icon="seti:javascript">

```js
const fs = require('fs')

const query = {
  role: 'user',
  contents: [
    { type: 'image', image: { type: 'embedded', mime_type: 'image/jpeg', data: fs.readFileSync('dog.jpg') } },
    { type: 'text', text: 'What do you see in this image?' },
  ],
}
for await (const output of agent.run(query)) {
  // ...
}
```

</TabItem>
<TabItem label="Rust" icon="seti:rust">

```rust
use ailoy::message::{Message, Part, Role};

let query = Message::new(Role::User).with_contents([
    Part::image_embedded("image/jpeg", std::fs::read("dog.jpg")?.into())?,
    Part::text("What do you see in this image?"),
]);
let mut stream = agent.run(query);
```

</TabItem>

## Tool calls and results

When the model wants a tool, its assistant message lists the call in `tool_calls`:

```json
{
  "role": "assistant",
  "contents": [{ "type": "text", "text": "Let me check the weather." }],
  "tool_calls": [
    {
      "type": "function",
      "id": "call_01HZX2",
      "function": { "name": "get_weather", "arguments": { "city": "Seoul" } }
    }
  ]
}
```

The agent runs the tool and adds a `tool` message with the same `id`:

```json
{
  "role": "tool",
  "id": "call_01HZX2",
  "contents": [{ "type": "value", "value": 12.3 }]
}
```

If the tool fails, the error comes back as a `tool` message too, so the model can see it and recover. The agent then calls the model again, and repeats until the model answers without calling a tool.
