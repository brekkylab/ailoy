An agent calls the tools its spec names in `tools`: the built-in ones on this page, functions of your own, and the tools of an [MCP server](/docs/guides/using-mcp/) or of the [browser](/docs/guides/using-browser/).

## Built-in tools

### A shell and files

An agent whose spec has `use_sandbox` (`sandbox()` in Rust) works in a sandbox Ailoy makes for it, and gets a shell and tools to read and change files in it, with nothing else to call. Which tools come with the shell depends on the model's org:

| Org | Tools |
| --- | --- |
| `openai` | `shell`, `apply_patch`, `imgread` |
| `google` | `shell`, `read_file`, `write`, `edit`, `imgread` |
| `deepseek-ai`, `moonshotai`, `zai-org`, `Qwen`, `LGAI-EXAONE` | `shell`, `read`, `write`, `edit` |
| Any other, `anthropic` included | `shell`, `read`, `write`, `edit`, `imgread` |

| Tool | What it does |
| --- | --- |
| `shell` | Runs a command, with an optional timeout in seconds. |
| `read` | Reads up to 2,000 numbered lines of a text file, or `limit` lines from line `offset`. |
| `read_file` | Reads up to 2,000 lines of a text file, or the lines from `start_line` to `end_line`. |
| `write` | Writes a text file, replacing one already at that path. |
| `edit` | Replaces an exact string that occurs once in a text file, or, with `replace_all`, every occurrence of it. |
| `apply_patch` | Adds, deletes, updates and moves files, from a patch in the format Codex uses. |
| `imgread` | Reads a PNG, JPEG, GIF or WebP image of up to 5 MB and gives it to the model as an image. |

`imgread` is left out for `deepseek-ai`, `moonshotai`, `zai-org`, `Qwen` and `LGAI-EXAONE` because their backends pass a tool result to the model as text, so the model would get a label in place of the image.

The seven tools in the table come with `use_sandbox`, without being named in `tools`, and run in the agent's sandbox, as in [Giving an agent a sandbox](/docs/guides/sandbox/); an agent without one does not get them. The sandbox is made with the agent and removed when the agent is closed. In between, virtx stops an idle sandbox's VM and boots it again over what it wrote when it is next needed, so a later call finds the files as the last one left them.

### The web

`web_search` and `web_fetch` are named in the spec's `tools` (in Rust, `web_search_tool()` and `web_fetch_tool()` add them); they do not come with the sandbox. The two tools run in your program's process, not in the sandbox, so they work without one.

- `web_search` answers with each result's title, URL, a short description and the engine or API it came from: up to 10 results, or up to 20 when the model asks for more. How it searches is set for the whole program with `set_web_search_provider` (`setWebSearchProvider`), and a turn searches with the provider set when it starts:

  | Provider | How it searches | Needs |
  | --- | --- | --- |
  | `web` (the default) | The result pages of Google, Bing, DuckDuckGo, Startpage, Yahoo, Mojeek and Yandex, one engine a call in turn. When one blocks or finds nothing, the next takes over. Brave and Naver are searched through their APIs below. | Nothing |
  | `brave` | The Brave Search API. | `BRAVE_API_KEY` |
  | `tavily` | The Tavily API. | `TAVILY_API_KEY` |
  | `exa` | The Exa API. | `EXA_API_KEY` |
  | `naver` | Naver's web document search API. | `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` |

  Search engines turn away requests that look automated, from a server's address most of all, so `web` suits a program on your own computer; on a server, use an API. A provider whose key is missing makes the agent's turn fail. For a search of your own, register a function under the name `web_search` as in [Your own functions](#your-own-functions).
- `web_fetch` fetches one URL. An HTML page comes back as its visible text (the default), as Markdown, or as the HTML itself; any other body, such as JSON, comes back as it is. A long body comes in pieces, and the model asks for the next one with `offset`; only the body's first 2 MiB are read. It makes at most one request a second to a host, and only to addresses on the public internet: loopback, the local network and cloud metadata addresses are refused.

## Your own functions

A function of your program becomes a tool once it is registered with a **tool description**: the name the model calls it by, what it does, and a JSON schema for its arguments. Registering answers the tool's name, which the spec lists in `tools`. In Rust you build the description with `ToolDescBuilder` and register it with the function as a pair on the `tools` of `default_provider()`, which answers the names to give `tools(...)`.

This gives the agent `order_status`, which looks an order up by its id:

<Tabs syncKey="lang">

<TabItem label="Python" icon="seti:python">

```python
import asyncio

from ailoy import Agent, register_tool

ORDERS = {"A-1001": {"status": "shipped", "eta": "2026-10-24"}}


def order_status(order_id: str) -> dict:
    if order_id not in ORDERS:
        raise KeyError(f"no order {order_id}")
    return ORDERS[order_id]


async def main() -> None:
    name = register_tool(
        {
            "name": "order_status",
            "description": "Look up an order's status and expected delivery date by its id.",
            "parameters": {
                "type": "object",
                "properties": {"order_id": {"type": "string", "description": "The order id, such as A-1001"}},
                "required": ["order_id"],
            },
        },
        order_status,
    )

    agent = await Agent.from_spec({"model": "anthropic/claude-haiku-5-5", "tools": [name]})

    async for output in agent.run("When does order A-1001 arrive?"):
        for part in output["message"]["contents"]:
            if part["type"] == "text":
                print(part["text"])

    await agent.close()


asyncio.run(main())
```


</TabItem>
<TabItem label="Node.js" icon="seti:javascript">

```js
const { Agent, registerTool } = require('@brekkylab/ailoy')

async function main() {
  const orders = { 'A-1001': { status: 'shipped', eta: '2026-10-24' } }

  const name = registerTool(
    {
      name: 'order_status',
      description: "Look up an order's status and expected delivery date by its id.",
      parameters: {
        type: 'object',
        properties: { order_id: { type: 'string', description: 'The order id, such as A-1001' } },
        required: ['order_id'],
      },
    },
    ({ order_id }) => {
      if (!(order_id in orders)) throw new Error(`no order ${order_id}`)
      return orders[order_id]
    },
  )

  const agent = await Agent.fromSpec({ model: 'anthropic/claude-haiku-5-5', tools: [name] })

  try {
    for await (const { message } of agent.run('When does order A-1001 arrive?')) {
      for (const part of message.contents) {
        if (part.type === 'text') console.log(part.text)
      }
    }
  } finally {
    await agent.close()
  }
}

main()
```

<TabItem label="Rust" icon="seti:rust">

```rust
use ailoy::{
    Agent,
    agent::{AgentSpec, default_provider},
    datatype::Value,
    message::{Message, Part, Role},
    to_value, tool_func,
    tool::ToolDescBuilder,
};
use futures::StreamExt as _;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let desc = ToolDescBuilder::new("order_status")
        .description("Look up an order's status and expected delivery date by its id.")
        .parameters(to_value!({
            "type": "object",
            "properties": {"order_id": {"type": "string", "description": "The order id, such as A-1001"}},
            "required": ["order_id"]
        }))
        .build();
    let func = tool_func!(|args: Value| -> Value {
        match args.pointer("/order_id").and_then(Value::as_str) {
            Some("A-1001") => to_value!({"status": "shipped", "eta": "2026-10-24"}),
            Some(id) => Value::string(format!("error: no order {id}")),
            None => Value::string("error: no order_id"),
        }
    });
    let names = default_provider().write().unwrap().tools.set((desc, func));

    let spec = AgentSpec::new("anthropic/claude-haiku-5-5").tools(names);
    let agent = Agent::from_spec(spec, Vec::new(), None).await?;

    let query = Message::new(Role::User).with_contents([Part::text("When does order A-1001 arrive?")]);
    let mut stream = std::pin::pin!(agent.run(&query));
    while let Some(output) = stream.next().await {
        let message = output?.message;
        if message.role == Role::Assistant {
            for text in message.contents.iter().filter_map(Part::as_text) {
                println!("{text}");
            }
        }
    }
    agent.close().await?;
    Ok(())
}
```

How the function is called:

- **Python**: the arguments come as keyword arguments, named as in the schema, and the function may be `async`.
- **Node.js**: they come as one object, and the function may return a promise.
- **Rust** registers a description and a `ToolFunc` as a pair with `tools.set(...)` on `default_provider()`, which answers the names of what it provides. `tool_func!` builds one from a closure that takes the arguments as a `Value`; with `async` before the closure, its body can `.await`.

The function returns what a message can hold: null, a boolean, a number, a string, or a list or object of those. In Python and Node.js an exception, or a rejected promise, does not end the run: the model gets it as the result, such as `error: KeyError: 'no order B-9'` from the Python function above, and can try something else.

Tool calls the model makes in one step run at the same time, the seven built-in tools above among them: a sandbox runs many processes at once. A function of yours may be called again before its last call has returned.

A Python or Node.js function runs in your program, not in the sandbox. To run a command or read a file there, it gets the agent's sandbox from your virtx client by its id, `await client.get_sandbox(agent.sandbox_id)` (`client.getSandbox(agent.sandboxId)`), and calls it, such as `sandbox.exec(...)` or `sandbox.read_file(...)`. In Rust, a closure that also takes `sandbox: &Sandbox` gets the agent's sandbox, as the built-in tools do, and `ailoy::tool::{exec, read, write}` run a command and read and write a file in it.

Tools are registered by name for the whole process, the built-in ones included. An agent makes the tools its spec names as each turn starts, so registering a name again, `shell` among them, replaces its description and function for every turn after that, an existing agent's included. `remove_tool_provider` (`removeToolProvider` in Node.js, `tools.remove(name)` on `default_provider()` in Rust) takes a name out.

## How much of a result the model reads

The agent keeps at most 30,000 characters of each part of a tool result, for built-in tools and your own alike:

- A longer part keeps its first and last 15,000 characters around a note of how many were cut, so a file read whole may reach the model with its middle missing.
- A Python or Node.js function's result, a string included, becomes a value part. A value part is measured in characters of its JSON, and once that passes 30,000, the model gets the JSON text as a string with its middle cut.
- `web_fetch` and `shell` size their results to fit: a long page comes in pieces that each reach the model whole, and `shell` cuts a long stdout or stderr itself, keeping its start and end around a note of how many characters it lost.
