A sandbox is a Linux microVM where an agent runs commands and works with files, isolated from your machine. Sandboxes run on a [virtx](https://virtx.sh/docs/) server. You create one with the virtx package, which the Ailoy install already includes:

| Language | virtx package |
| --- | --- |
| Python | `virtx` (`from virtx import Client`) |
| Node.js | `@brekkylab/virtx` |
| Rust | The `virtx` crate. `ailoy::console::Sandbox` is the same type as `virtx::Sandbox`. |

This page covers what an agent needs from a sandbox. For everything else about sandboxes (servers, images, volumes, GPUs), see [virtx's docs](https://virtx.sh/docs/).

## Create a sandbox and pass it to an agent

Pass a sandbox to `.sandbox(...)` on the `AgentBuilder`. The agent gets a shell and file tools that run inside it ([the full list](/docs/guides/tools/#shell-and-file-tools)).

This example builds an image with matplotlib installed, creates a sandbox from it, and has the agent draw a plot:

<Tabs syncKey="lang">

<TabItem label="Python" icon="seti:python">

```python
import asyncio
from pathlib import Path

from ailoy import AgentBuilder
from virtx import Client, Recipe


async def main() -> None:
    client = Client.spawn()

    # Kept on the server under its tag: later sandboxes boot it without building again.
    recipe = Recipe("python:3.12-slim-trixie").run("pip install --no-cache-dir matplotlib")
    await client.build_image(recipe, "plot:latest").complete()

    sandbox = await client.create_sandbox("plot:latest")

    agent = await (
        AgentBuilder("anthropic/claude-haiku-5-5")
        .instruction("Write what you are asked for into /artifacts.")
        .sandbox(sandbox)
        .build()
    )
    async for _ in agent.run("Plot y = x^2 for x from -5 to 5 into /artifacts/square.png."):
        pass

    Path("square.png").write_bytes(await sandbox.read_file("artifacts/square.png"))
    await agent.close()
    await sandbox.remove()


asyncio.run(main())
```

const { AgentBuilder } = require('@brekkylab/ailoy')
const { Client, Recipe } = require('@brekkylab/virtx')

  // Kept on the server under its tag: later sandboxes boot it without building again.
  const recipe = new Recipe('python:3.12-slim-trixie').run('pip install --no-cache-dir matplotlib')
  await client.buildImage(recipe, 'plot:latest').complete()

    .instruction('Write what you are asked for into /artifacts.')
    .sandbox(sandbox)

  writeFileSync('square.png', await sandbox.readFile('artifacts/square.png'))

}

<TabItem label="Rust" icon="seti:rust">

```rust
use ailoy::{
    agent::AgentBuilder,
    message::{Message, Part, Role},
};
use futures::StreamExt as _;
use virtx::{Client, Files as _, Recipe, SandboxCreateArgs};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let client = Client::spawn_virtx([] as [&str; 0]).await?;

    // Kept on the server under its tag: later sandboxes boot it without building again.
    let recipe = Recipe::new("python:3.12-slim-trixie").step("pip install --no-cache-dir matplotlib");
    client.build_image(recipe, "plot:latest").complete(false).await?;

    let sandbox = client
        .create_sandbox(&SandboxCreateArgs::new("plot:latest"))
        .await?;

    let mut agent = AgentBuilder::new("anthropic/claude-haiku-5-5")
        .instruction("Write what you are asked for into /artifacts.")
        .sandbox(sandbox.clone())
        .build()
        .await?;
    let query = Message::new(Role::User)
        .with_contents([Part::text("Plot y = x^2 for x from -5 to 5 into /artifacts/square.png.")]);
    let mut stream = agent.run(query);
    while let Some(output) = stream.next().await {
        output?;
    }
    drop(stream);

    std::fs::write("square.png", sandbox.read_file("artifacts/square.png", 0, None).await?)?;
    sandbox.remove().await?;
    Ok(())
}
```

Things to know:

- **Your code owns the sandbox.** The agent never starts, stops or removes it, and closing the agent leaves it running. Remove it yourself, as the example does. If `Client.spawn()` started the server, its sandboxes are also removed when your program exits.
- **Calls run in parallel.** Your code can use the sandbox while the agent works, and the tool calls the agent makes in one step run at the same time.
- **Errors come from virtx.** A failed sandbox call raises virtx's `VirtxError`.

An agent without a sandbox still works with tools that don't need one: your own functions, `web_search`, `web_fetch`, MCP servers and a browser. It has no shell or file tools, and it can't use [skills](/docs/guides/skills/), because it reads them from the sandbox.

## Decide where files go

Files in a sandbox come from three places, and each lasts a different amount of time:

| Location | What to put there | How long it lasts | virtx docs |
| --- | --- | --- | --- |
| The image | Programs and packages | Until you remove the image. Every sandbox created from it starts with these files. | [Images](https://virtx.sh/docs/guides/images/) |
| A volume | Inputs, skills, and results you want back | Until you remove the volume. Several sandboxes can mount it, and your code can read and write it while they run. | [Mounting volumes](https://virtx.sh/docs/guides/mounting-volumes/) |
| The sandbox's own disk | Everything else the agent writes, such as packages it installs | Until you remove the sandbox | [Removing a sandbox](https://virtx.sh/docs/guides/setting-sandboxes/#remove-a-sandbox) |

As a rule:

- Install packages that every run needs in the **image**, so the agent doesn't install them each time.
- Put files you give the agent, and files you want back, on a **volume**.

The examples in [ailoy-examples](https://github.com/brekkylab/ailoy-examples) all follow this pattern: they build the image once, put the skill and inputs on named volumes, and copy results out at the end.

### Build an image from the command line

The `virtx` command builds images from a Dockerfile, with the same syntax as `docker`. It comes with the virtx package: `pip install ailoy-py` puts it in your environment's `bin/` folder, and `@brekkylab/virtx` puts it in `node_modules/.bin`. You can also run it with `uvx virtx` or `npx @brekkylab/virtx`.

```sh
virtx build -t plot:latest .    # from ./Dockerfile
virtx images                    # the images on the server
```

Then create sandboxes from `plot:latest`. See virtx's [Images](https://virtx.sh/docs/guides/images/) for the full command.

## Pass files in and get results out

1. Before the turn, write the agent's input files to a volume mounted in its sandbox. Mount it read-only if the agent shouldn't change them.
2. In the instruction, tell the agent where to read inputs and where to save results.
3. After the turn, read the results from the volume or from the sandbox, as the example above does with `read_file`.

See virtx's [Reading and writing files](https://virtx.sh/docs/guides/reading-writing-files/) for the calls.

## Continue the work later

An agent's progress lives in two places: its history and its sandbox's files. To continue where a run stopped:

1. Save the agent's history (`agent.history`).
2. Find the same sandbox again with virtx's `get_sandbox`.
3. Build a new agent with `.history(saved_messages)` and `.sandbox(sandbox)`.

A sandbox's own files are deleted when the sandbox is removed. Keep anything a later run needs on a volume.

## Sandbox options

`create_sandbox` accepts these options, among others:

| Option | Use it for | virtx docs |
| --- | --- | --- |
| `volumes` | Folders where the agent reads your files and saves its results. | [Mounting volumes](https://virtx.sh/docs/guides/mounting-volumes/) |
| `network` | Whether commands in the sandbox can reach the internet. On by default. `web_search` and `web_fetch` run in your program, so they work either way. | [Networks and ports](https://virtx.sh/docs/guides/networks-ports/) |
| `ports` | Reaching a server the agent starts in the sandbox. | [Networks and ports](https://virtx.sh/docs/guides/networks-ports/) |
| `vcpus`, `memory_mib`, `disk_gib` | CPU, memory and disk for heavy commands and for files outside volumes. | [Setting up sandboxes](https://virtx.sh/docs/guides/setting-sandboxes/) |
| `gpu`, `gpu_memory_mib` | A GPU through Vulkan, for work such as deep learning. | [Using GPUs](https://virtx.sh/docs/guides/using-gpus/) |
| `abins` (`.abin(name)` in Rust) | virtx's built-in programs at `/abin`, such as `index`, `docread` and `display`. Each one that has a `SKILL.md` becomes one of the agent's [skills](/docs/guides/skills/#skills-from-built-in-programs). | [Setting up sandboxes](https://virtx.sh/docs/guides/setting-sandboxes/) |

Node.js uses camelCase (`memoryMib`, `diskGib`, `gpuMemoryMib`). Rust sets them on `SandboxCreateArgs`. To run the server on another machine, see virtx's [Hello world](https://virtx.sh/docs/hello-world/).

## Troubleshooting

virtx errors have a `source` (`server`, `job`, `transport` or `client`) and, when they come from the server, an HTTP `status`. Use those to tell errors apart, not the message text ([Errors](https://virtx.sh/docs/reference/api/#errors)).

| Error | Cause and fix |
| --- | --- |
| `` `<command>` exited with <code> `` from `build_image(...).complete()` | A step in the recipe failed. The build log above the error shows each step's output (`STEP 1/2: …`). |
| `<image>: not found, or private and pulled without credentials` | The image name is wrong, or the image is private. |
| `no image here is tagged <tag>: pull it first` (status `404`) | Pull or build the image before you create a sandbox from it. |
| Status `400`, such as `abins: this server has no program called …` | An option is unknown or out of range. The message names it. |
| Status `409` | The name is taken, the volume is in use, or the sandbox's VM has exited. |
| `this server was built without a GPU` (status `422`) | This server can't provide a GPU. Use a release build of the virtx server. |
| Vulkan finds no device in a GPU sandbox | The host has no Vulkan driver. On Linux or Windows, install your GPU maker's driver. On macOS, virtx includes its own. |
| A command in the sandbox can't reach a host | The sandbox was created with `network` off. Turn it on, or fetch the data in your program and write it into the sandbox. |
| The agent's file isn't in `/artifacts` | The agent saved it somewhere else. Name the folder in the instruction, as the examples do, and check the agent's last message for the path. |
| `boot_failed` when the first sandbox starts | See [Installation troubleshooting](/docs/guides/installation/#troubleshooting). |
